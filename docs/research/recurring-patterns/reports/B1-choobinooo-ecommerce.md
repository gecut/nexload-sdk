### Important flow details and extraction cautions

- **C OTP:** `sendOtpForPurpose` normalizes, checks most recent phone/purpose cooldown, deletes prior matching records, creates code and calls SMS.ir; failed delivery deletes the new record (`auth.service.ts:158-227`). Verification queries phone, code, purpose and expiry, then deletes after user processing (`auth.service.ts:248-310`). The collection's `beforeChange` deletes by phone **without purpose** (`packages/core/src/collections/authentication/otp/hooks/before-change.ts:3`), so creating one purpose can remove another. The separate `utilities/otp/sender.ts:10` only generates/logs; `utilities/otp/verifier.ts:5` is a stub. Do not confuse those utilities with the active API implementation.
- **E SMS:** projection and delivery are separate stages; delivery rows store state, claim ownership and provider metadata. Defaults are five attempts, exponential delay from one minute up to one hour and stale claim recovery after five minutes (`packages/schema/src/notifications/notification-delivery-retry.ts:32`). Worker ownership guards reduce concurrent updates, but do not independently guarantee exactly-once external delivery (`apps/cms/src/jobs/sms-delivery.task.ts:106`, `:172`, `:231`; `apps/cms/src/jobs/sms-delivery.ts:28`). Actual provider support behind the generic HTTP endpoint is unverified.
- **C payment:** the callback uses gateway track ID, marks a reported failure or calls server-side verification, then redirects (`apps/api/src/http/payment-callback.ts:40`). Verification requires Zibal success and compares converted gateway amount to both recorded payment and expected order amount (`apps/api/src/rpc/services/payment.service.ts:224-322`). It returns early for existing success, so failure between payment success and order update requires particular recovery review.
- **E payment:** authenticated initiation creates/reuses a CMS attempt via idempotency key, sends a Zibal request and attaches authority (`apps/api/src/rpc.ts:419`). Callback/verification converts rial to integer toman and rejects amounts not divisible by ten (`apps/api/src/modules/payments/payment-verification.ts:4`). CMS checks prior verification, locks relevant records, compares attempt amount, records outcome and applies timely/late order policy (`apps/cms/src/modules/payments/payment.operations.ts:198`, `apps/cms/src/modules/payments/payment-verification-policy.ts:5`). Provider behavior and race-safety were not tested here.

## 3. Best implementation per pattern

- **SMS queue and delivery records:** E's notification projector, delivery entity and worker are the strongest source for a reusable design: persistent state, claims, recovery and retry are explicit. Separate order-template mapping and PostgreSQL-specific locking from provider transport. Preserve provider-side idempotency as a contract, not a claim of exactly-once delivery.
- **OTP:** E's hashed challenge, expiry, attempt limit and atomic consumption are the stronger security starting point; combine with C's clear SMS.ir transport and failure handling only after fixing E's unconfigured-transport logging behavior and deciding delivery/retention semantics. C's helper is not an OTP verifier.
- **Payment:** E's separate attempt/verification entities, transaction, duplicate handling and late-payment rules are the stronger domain foundation. Use C as evidence for staged custom-order payments and a more explicit Zibal verification predicate; neither implementation is already a configurable multi-provider gateway library.
- **Checkout, stock, discounts, shipping:** E's guarded reservation, redemption records and outbox are stronger extraction references. C contributes custom orders, deposits and its simpler calculation/validation functions; avoid baking either store's status vocabulary into a generic interface.
- **Catalog/reviews:** E's canonical product/variant entities provide a schema starting point; C's asynchronous review rating and facet tasks are useful optional behaviors. Full review lifecycle was not compared.
- **Persian fields, env, logging, health and Payload operations:** reuse the already consumed SDK packages, with E's semantic field definitions and C's admin display as examples. Prefer extensions or integration recipes over parallel foundational modules.

## 4. Variations / divergences a reusable module must support as config

- SMS: direct synchronous OTP versus durable asynchronous order messages; SMS.ir template verification and bulk message requests versus E's generic HTTP template/variables endpoint. Provider credentials, template IDs, parameter names, sender, environment policy, timeouts, response mapping and redacted logging belong at the transport boundary. Kavenegar requires a new secure adapter, not reuse of C's HTTP helper.
- Delivery persistence: collection names and access, event-to-template mapping, queue/worker scheduling, batch size, claim lease, retry/backoff, retention, provider reference and idempotency behavior. E's locking is PostgreSQL-specific. Define what happens when a provider accepts a request but acknowledgement is lost.
- OTP: phone normalization, purpose isolation, code entropy and hashing, expiry, cooldown, verification attempt limit, atomic consume, account creation/reset behavior, rate-limit store, non-production transport and cleanup. Current C collection-level deletion crosses purpose boundaries; E's logging fallback requires remediation.
- Payment: adapter-specific initiation/callback/verify formats and success predicates, merchant configuration, request timeouts, retry/idempotency keys, callback routing, persistence and authorization; explicit internal currency and gateway-unit conversion. Both observed implementations are Zibal-coupled; Zarinpal and IDPay are candidate future adapters, not confirmed implementations in this batch.
- Commerce: custom versus catalog orders, full/deposit/final payments, status transitions, inventory reservation/expiry/release, discounts and eligibility, shipping pricing, refunds and late confirmations. Make order transition and transaction boundaries explicit, including recovery after partial failure.
- Operational context: Payload local API versus CMS operation boundary, database/locking implementation, service roles, distributed versus process-local rate limits, worker deployment and existing SDK versions. Persian/Jalali display, phone and currency conventions should be configurable over shared semantic primitives.

## 5. Candidate modules ranked by frequency × effort saved

Ranking is qualitative: frequency counts only the two repositories, while effort saved reflects observed implementation complexity; it is not measured time saved.

1. **Payment attempts and verification, with provider adapters** — 2/2; high effort. E provides transaction and records; C adds staged payments. Begin with Zibal; provider abstraction and other gateways are prospective.
2. **OTP challenge and SMS transport** — 2/2; high effort. Shared purpose, expiry, throttling and provider integration recur, but the storage/security and delivery differences require a defined contract.
3. **Checkout / order and inventory primitives** — 2/2; high effort, but extraction must preserve different catalog/custom and reservation rules. Favor composable operations over a fixed commerce application.
4. **SMS notification delivery queue and Payload collections** — durable queue confirmed in 1/2, high effort; SMS is 2/2. E is a substantial reference, while C demonstrates a direct-send deployment. Treat as an optional persistence/worker integration, not a prerequisite for OTP.
5. **Discount and shipping policies** — 2/2; moderate effort, with differing eligibility, redemption and cost rules.
6. **Catalog, variants and review building blocks** — 2/2; moderate effort, but product modeling and moderation are store-specific; extract only stable primitives.
7. **Persian field and operational integration recipes** — 2/2; moderate incremental savings; extend existing `@nexload-sdk/payload-fields`, `payload-schema`, `env`, `logger`, healthcheck and operations packages rather than reimplementing them.

Not established in this batch: a reusable wallet, invoice/factor, Telegram bot, email transport, S3/MinIO integration, or specific Iranian national-code/IBAN validator. These were not exhaustively audited, so this is an evidence gap rather than a claim of absence.
