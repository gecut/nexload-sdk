## 3. Best implementation per pattern

- **SMS:** combine Rasad's provider contract and Payload job boundary (`apps/cms/src/integrations/sms/types.ts`, `apps/cms/src/domain/sms/send-sms-task.ts`) with Cloud's Kavenegar transport (`apps/server/src/modules/notifications/services/kavenegar.service.ts`). Neither is a complete generic delivery module; Rasad's provider is simulated, and its per-invitation success state loses per-recipient detail.
- **Payment gateway:** Cloud's `packages/payment/src/index.ts` is the clearest transport starting point, with the callback service as behavioral reference. Rework persistence, return URL validation, concurrency/idempotency and recovery before extraction; do not assume the existing transaction settles all race conditions.
- **OTP:** Cloud's `apps/server/src/modules/auth/services/otp.service.ts` shows lifecycle and attempt limits; replace process-local storage and assess secure code storage/atomic consumption before production reuse.
- **Persian input and dates:** Rasad's `apps/cms/src/lib/jalali.ts` is the best Jalali parsing/timezone reference; Cloud's `apps/admin/src/utils/phone.ts` covers phone prefixes; Kolahat's `src/lib/product-pricing.ts` covers numeric input. First check existing SDK Payload field overlap.
- **Tier pricing:** Kolahat's `src/lib/product-pricing.ts` has a focused calculation and explicit tier validation with test source; use it as a starting point, not as server-authoritative stock or checkout.
- **Analytics and messaging:** Umami's `src/umami/client.ts`, `src/report/coordinator.ts`, and `src/telegram/bot.ts` offer the strongest respective references. Their reporting semantics and single-replica assumptions must remain configurable.
- **Roles, invoices and draft state:** Rasad's access functions, Cloud's invoice commands, and Calc's versioned draft codec are useful examples, but each is too domain-specific or narrow to recommend direct extraction without more projects.

## 4. Variations / divergences a reusable module must support

- SMS: direct OTP versus queued transactional messages; plain text versus template tokens; provider-specific response mapping; per-recipient outcomes, retry/idempotency and persistent audit with sensitive-data minimization; selectable real/simulated provider and configurable task storage/runner.
- Payments: provider credentials and endpoints, callback/return URL policy, Toman versus Rial units, verification statuses including repeated callbacks, durable attempt and correlation records, atomic settlement and tenant ownership; support adapters only when their actual contracts are verified.
- OTP/auth: normalized phone formats, expiry, attempts and rate limits; shared atomic storage versus single process, session issuance and role policy per application.
- Persian utilities: Persian/Arabic/ASCII digits, validation versus display, calendar/timezone, date-only versus absolute instant, currency units and precision. Reuse SDK fields/formatters where behavior matches; don't conflate display with financial arithmetic.
- Commerce: retail versus wholesale tier and minimum quantities, product variants, availability and custom production; UI estimates are not authoritative inventory/checkout. An order status timeline needs configurable transitions, not a hard-coded demo sequence.
- Reports/dispatch: Umami instance and project mapping, timezones, report sections and event definitions, Telegram chat authorization, scheduling, retry/backoff and deployment topology. In-memory throttling is not distributed coordination.
