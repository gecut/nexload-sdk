# B2-faralist — recurring-pattern research

Research date: 2026-11-22. Evidence paths below are relative to the named project root. Source inspection only; no tests, live gateways, queues, databases, or deployments were run. Quality is a subjective extraction-readiness score: 1 = fragment/mock, 3 = useful but coupled or unverified, 5 = strong reusable implementation with few evident gaps. It is not a production-readiness score. `faralist.com` and `faralist-catalog` contain substantial pre-existing working-tree changes; this report reflects files present locally, including relevant Git-ignored source files, not just committed code. README descriptions can lag current source.

## 3. Best implementation per pattern

- **Payment adapter/callback:** Start with `faralist.com/packages/billing/src/index.ts` and `apps/api/src/core/http/payment-callback.ts` as design inputs, not drop-in production code. Zibal has amount checking, timeout and production mock guards; reconcile currency semantics and concurrent settlement with `billing.service.ts` before extraction. Zarinpal and mock behavior differ materially. No existing payment-engine usage was confirmed.
- **Subscription calculation:** `faralist.com/packages/billing/src/index.ts` has isolated BigInt calculations and tests; make plan, credit and coupon policy explicit instead of exporting FaraList rules as universal defaults.
- **OTP/auth:** `faralist.com/packages/auth/src/index.ts` and `apps/api/src/modules/auth/auth.service.ts` provide the only observed end-to-end candidate. Separate provider, storage and session concerns; replace process-local rate limits where distributed enforcement is needed, and review pepper and sensitive logging.
- **SMS:** `faralist.com/packages/auth/src/index.ts`, `packages/db/src/schema/sms.ts`, and `apps/worker/src/jobs/sms.job.ts` show provider, templates, logs and queue. Extract interfaces and delivery semantics first; there is no evidenced Payload collection to copy.
- **Outbox/worker:** `faralist.com/packages/db/src/index.ts` and `apps/worker/src/index.ts` are useful starting points. Fix or explicitly redesign claim lifetime, deduplication and crash recovery before treating this as a reliable reusable dispatcher.
- **Media:** `faralist.com/packages/media/src/{index,local,processing}.ts` is the clearest separated port/adapter and processing pipeline; integrate lifecycle and authorization only through explicit host application interfaces.
- **Catalog/formatting:** `faralist-catalog/src/data/catalog.ts` and `src/features/catalog/catalog-product.ts` give the richest standalone read model; `faralist-landing/lib/landing/demo.ts` is a smaller digit/price utility example. Neither demonstrates a reusable transactional commerce backend.
- **Analytics:** `faralist-catalog/src/lib/analytics.ts` illustrates browser transport; pair only with a separately designed ingestion contract, since compatibility with the monorepo worker was not established.

## 4. Variations a reusable module must support

- Payment provider and credential configuration, callback shape, sandbox versus mock, currency/unit conversion, timeouts, verified amount/reference, repeat verification and reconciliation. Tie settlement to persisted expected terms; handle concurrent callbacks and provider success followed by local failure.
- Plan period, renewal/upgrade, actually-paid proration, credits, coupon order, invoice and entitlement policies are application choices, not gateway responsibilities.
- OTP delivery provider/template, expiry and attempts, phone normalization, secure pepper sourcing, rate-limit store, session duration, cookie scope and admin/owner roles. Direct OTP delivery and queued notifications are distinct paths.
- SMS event-to-template mapping, tokens, delivery statuses, retry policy, quiet hours/time zone, logging/redaction and provider-specific capabilities. Persistence adapters could target Drizzle or Payload, but only Drizzle is evidenced here.
- Queue backend, job names, retry/backoff/retention, process isolation, durable claims, idempotency, scheduling and monitoring. Redis/BullMQ and SQL outbox are separate interfaces.
- Media local versus object storage, staging/public/quarantine, authorized ownership and quotas, supported formats, pixel/byte limits, variant widths, metadata stripping, retention and cleanup. Object storage remains a candidate, not an observed adapter.
- Catalog source (static JSON versus API), variant/stock and unpriced behavior, category hierarchy, sorting, IRT versus USD, Persian/Arabic digits and locale, image fallback and analytics transport.
