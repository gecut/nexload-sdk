## Built-In Presets Catalog

`@nexload-sdk/payload-editor` provides five curated presets designed for distinct content creation needs:

| Preset Name | Target Use Case | Included Highlights |
|---|---|---|
| `compact` | Comments, brief bios, small callouts | Bold, italic, underline, link, inline toolbar only. No headings or blocks. |
| `standard` | General descriptions, standard rich-text | Paragraphs, lists, blockquotes, links, basic formatting with sticky toolbar. |
| `structured-content` | Marketing landing pages, documentation | Headings (H1-H6), horizontal rules, image/file uploads, alignment tools. |
| `article` | Full blog posts, publications | Structured content plus inline code blocks, relationship embeds, and sub/superscript. |
| `product-description` | E-commerce product catalogs | Constrained headings (H2-H4), bullet lists, links, image gallery embeds. |

```ts
import { createEditor } from "@nexload-sdk/payload-editor";

export const standardEditor = createEditor({ preset: "standard" });
export const articleEditor = createEditor({ preset: "article" });
```

***

## Defining an Organization Preset

Standardize rich-text behavior across multiple projects or collections using `defineEditorPreset`:

```ts
import { createEditor, defineEditorPreset } from "@nexload-sdk/payload-editor";

// 1. Create a reusable corporate preset
export const corporateArticlePreset = defineEditorPreset({
  features: {
    paragraph: true,
    heading: {
      sizes: ["h2", "h3"], // Forbid H1 to maintain page SEO hierarchy
    },
    bold: true,
    italic: true,
    link: {
      autoLink: true,
      maxDepth: 1,
    },
    upload: {
      allowedCollections: ["media"],
      maxDepth: 1,
    },
    blockquote: true,
  },
});

// 2. Consume across collections
export const editor = createEditor({ preset: corporateArticlePreset });
```

***

## Extending with Native Lexical Blocks

When you need custom Lexical features that aren't part of the core preset (such as Payload's native `BlocksFeature`), use `extendFeatures`:

```ts
import { BlocksFeature } from "@payloadcms/richtext-lexical";
import { createEditor } from "@nexload-sdk/payload-editor";
import { CalloutBlock, GalleryBlock } from "@/blocks";

export const richArticleEditor = createEditor({
  preset: "article",
  extendFeatures: [
    BlocksFeature({
      blocks: [CalloutBlock, GalleryBlock],
    }),
  ],
});
```

`extendFeatures` appends providers after managed features. If a native provider replaces a built-in feature, set the managed key to `false` in `features`.

***

## Troubleshooting & Common Pitfalls

### 1. Editor Renders with Default Payload Controls Instead of Preset

* Ensure you assign the returned editor provider to the `editor` property of the `richText` field or Payload's root `editor` configuration:
  ```ts
  {
    name: "content",
    type: "richText",
    editor: myConfiguredEditor, // Must be assigned here
  }
  ```

### 2. Heading Sizes In Toolbar Don't Match Override

Remember that arrays in `features` **replace** rather than concatenate:

```ts
// Toolbar will ONLY offer H2 and H3
features: {
  heading: { sizes: ["h2", "h3"] },
}
```

### 3. Missing Peer Dependency Error

`@payloadcms/richtext-lexical` must be explicitly installed in your application:

```bash
pnpm add @payloadcms/richtext-lexical
```

Ensure its version matches your `payload` core version (`3.85.0` or higher).

# Overview & Quick Start

Deterministic semantic configuration, presets, and feature sets for Payload CMS's Lexical editor.

**Topic:** overview
**Package:** `@nexload-sdk/payload-editor` v1.1.0
**Canonical page:** https://gecut.github.io/nexload-sdk/packages/payload-editor/
**Package:** `@nexload-sdk/payload-editor`

**Current released version:** `1.1.0`

Semantic, deterministic Payload Lexical editor configuration.

[npm](https://www.npmjs.com/package/@nexload-sdk/payload-editor) · [Source](https://github.com/gecut/nexload-sdk/tree/main/packages/payload-editor)

`@nexload-sdk/payload-editor` transforms an explicit semantic feature definition into the official Payload CMS Lexical editor provider. It provides teams with named presets, deterministic feature merge rules, and safe extension seams without cluttering collection configurations with verbose Lexical boilerplate.

***

## 10-Second Code Snippet

```ts
import { createEditor } from "@nexload-sdk/payload-editor";
import type { CollectionConfig } from "payload";

// 1. Define explicit editor policy from preset
const blogEditor = createEditor({
  preset: "article",
  features: {
    heading: { sizes: ["h2", "h3"] }, // Restrict heading sizes
    upload: { allowedCollections: ["media"], maxDepth: 1 },
  },
});

// 2. Attach directly to Payload RichText field
export const Posts: CollectionConfig = {
  slug: "posts",
  fields: [
    { name: "content", type: "richText", editor: blogEditor },
  ],
};
```

***

## What You Get

* **Ready-to-Use Presets**: Built-in presets for common editorial workflows: `compact`, `standard`, `structured-content`, `article`, and `product-description`.
* **Deterministic Feature Merging**: Clear override semantics: `false` disables, `true` enables with defaults, objects shallow-merge, and array options replace.
* **Custom Organization Presets**: Define reusable corporate editor standards using `defineEditorPreset()`.
* **Native Extension Seam**: Seamlessly attach native Lexical features like `BlocksFeature` or custom AST nodes via `extendFeatures`.
* **Zero UI Bloat**: The package runs in server/config code, has no client React runtime, and declares no side effects.

## Feature State Semantics

In `createEditor({ features: { ... } })`:

* **Omitted key**: Inherits configuration from the active preset (or disabled if no preset is used).
* **`false`**: Completely disables and removes the feature from the editor toolbar.
* **`true`**: Enables the feature with default recommended options.
* **`{ ...options }`**: Enables the feature and shallow-merges your specific options. Any provided arrays replace preset arrays rather than appending.

## Managed Unicode Slugs

The `slugField` factory generates clean, URL-friendly slugs while preserving non-Latin scripts (such as Persian and Arabic):

```ts
import { slugField } from "@nexload-sdk/payload-fields";

const fields = [
  { name: "title", type: "text", required: true },
  ...slugField({
    source: "title",
    overrides: {
      slug: {
        admin: {
          position: "sidebar",
          description: "Auto-generated from title. Unlock to manually edit.",
        },
      },
    },
  }),
];
```

### Uniqueness & Collision Suffixing

* Slugs are unique by default (`unique: true`). When creating a document whose generated slug already exists, the factory automatically searches for non-colliding suffixes (`-2`, `-3`, up to `-50`).
* **Top-level only:** Uniqueness collision queries apply only to top-level fields. Slugs placed inside nested arrays or groups receive character normalization only.
* If migrating an existing database with duplicate slug values, resolve duplicates before creating unique indexes or pass `unique: false`.

### Slug Locking Mechanism

* When a document is created, `slugLock` defaults to `true`.
* Editing the source field updates `slug` while locked.
* Once locked documents are published, unlocking allows manual editing. While unlocked, source edits never change the slug. A locked slug follows source edits unless you pass `regenerateOnSourceChange: false`.

## Jalali (Persian Solar) Datepicker & Date Ranges

Store standard ISO datetimes while providing a rich Persian Solar calendar widget in Payload Admin:

```ts
import { jalaliDateField, jalaliDateRangeField, withJalaliTimestamps } from "@nexload-sdk/payload-fields";

const fields = [
  jalaliDateField({
    name: "eventDate",
    pickerAppearance: "dayAndTime", // Options: "dayOnly" | "dayAndTime" | "monthOnly" | "timeOnly"
    timeZone: "Asia/Tehran", // Default timezone
  }),
  jalaliDateRangeField({
    start: "registrationStart",
    end: "registrationEnd",
  }),
];

// Adds virtual read-only createdAtJalali and updatedAtJalali fields
export const collectionFields = withJalaliTimestamps(fields);
```

### Date Storage Guarantees

* The database always stores standard UTC ISO 8601 strings (e.g. `2026-07-24T08:30:00.000Z`).
* For `dayOnly` and `monthOnly`, dates store canonical noon (`12:00:00`) in `timeZone` (default `Asia/Tehran`). This prevents date shifts when users view or edit entries from different browser timezones.
* In `jalaliDateRangeField`, the end field includes server-side validation ensuring that the end date falls on or after the start date.

## Safe-Integer Money Fields

Prevent floating point inaccuracies by storing currency in integer minor units:

```ts
import { moneyField } from "@nexload-sdk/payload-fields";

const fields = [
  moneyField({
    name: "unitPrice",
    currency: "IRT", // Stored in Tomans
    minMinorUnits: 0,
    maxMinorUnits: 10_000_000_000,
  }),
  moneyField({
    name: "rialPrice",
    currency: "IRR", // Stored in Rials
    displayCurrency: "IRT", // Displayed as Tomans in Admin UI and list cell
  }),
];
```

### API Strings & Plugin Requirement

* In the Admin UI, users type numbers with Persian or Latin digits and thousands grouping.
* In REST, GraphQL, and Local API calls, values are stored as integers.
* **Critical Requirement:** `payloadFieldsPlugin()` is **REQUIRED** if money values are sent as strings through REST or Local API (e.g. `"۱۲۳٬۴۵۶"` or `"123456"`). Payload's core runs `parseFloat()` on number fields before field hooks run, which corrupts Persian digits. The plugin registers a `beforeOperation` hook that normalizes string values to safe integers before Payload processes them.

## Iranian Contact & Identity Fields

Standardize phone numbers, national identification, postal codes, and banking fields:

```ts
import {

const fields = [
```

### Validation & Localization

* Values written through any API are normalized server-side in `beforeValidate` (Persian digits converted, dashes/spaces removed).
* Validation errors are localized: admin sessions in `fa` (e.g. `fa-IR`) see Persian error messages; other languages see English error messages.
* Admin list views automatically display formatted strings via `FormattedCell` (e.g. `۰۹۱۲ ۳۴۵ ۶۷۸۹`, `۶۰۳۷-۹۹۱۲-۳۴۵۶-۷۸۹۰`).

## Troubleshooting & Common Pitfalls

### 1. Custom Admin Controls Fallback to Plain Inputs

If Payload Admin displays plain number or text inputs instead of the Jalali datepicker or formatted money input:

* Regenerate Payload's Import Map by running:
  ```bash
  pnpm payload generate:importmap
  ```
* Ensure `@payloadcms/ui` and `payload` are `>=3.85.0 <4.0.0` and React is `^19.0.0`.

### 2. Money Strings Rejected by REST or Local API

If sending string values like `"150000"` or `"۱۵۰٬۰۰۰"` fails validation or gets parsed as `NaN`:

* Ensure `payloadFieldsPlugin()` is registered in your `payload.config.ts` plugins array.
* The plugin interceptively normalizes string money values in `beforeOperation` before Payload's core `parseFloat()` runs.

### 3. Duplicate Slug Migration Errors

If adding `slugField` to an existing collection throws a unique constraint database error:

* Deduplicate existing documents before deploying the schema change, or temporarily configure `slugField({ unique: false })`.

## Storage & Contract Rules

### 1. Slugs & SlugLock

`slugField({ source: "title" })` returns an array of two Payload fields: `[slug, slugLock]`.

* Slugs are unique by default (`unique: true`). Top-level slug collisions automatically receive numeric suffixes (`-2`, `-3`) in the active locale.
* **Scope note:** Slug uniqueness collision resolution only applies to top-level slug fields. Slugs placed inside arrays or groups receive character formatting only.
* `slugLock` defaults to `true`. When locked, changing the source field will not mutate an existing slug, protecting indexed URLs.

### 2. Jalali Dates & Ranges

Dates are stored in the database as **standard ISO 8601 UTC strings** (e.g. `"2026-07-24T08:30:00.000Z"`).

* For `dayOnly` and `monthOnly` appearances, dates store canonical local noon (`12:00:00`) in `timeZone` (default `Asia/Tehran`), preventing date shifting across client timezones.
* `jalaliDateRangeField` groups two dates and validates that `endsAt >= startsAt`.

### 3. Money Values & Plugin Requirement

Money values are stored strictly as **integer minor units** (e.g. `100,000 Tomans` is stored as `100000`).

* **REST / Local API String Inputs:** `payloadFieldsPlugin()` is **REQUIRED** if money values are sent as strings (e.g. `"۱۲۳٬۴۵۶"` or `"123456"`). Payload core parses number-field strings with `parseFloat()` before field hooks run, corrupting Persian digits and thousands separators. The plugin's `beforeOperation` hook converts string values to safe integers before Payload parses them. Raw numbers work without the plugin.

### 4. Bilingual Validation Messages

Validation messages follow the active admin language (`req.i18n.language` or `useTranslation()`):

* Locales starting with `fa` (e.g. `fa`, `fa-IR`) receive Persian error messages.
* All other locales receive English error messages (v3 was always Persian).

### 5. Schema Adapter Scope

The `./schema` subpath exposes `schemaFields` for `@nexload-sdk/payload-schema`. In 4.0, `iranAddressField` and `jalaliDateRangeField` are not included in `./schema` (compound group/row schemas require entity-level composition).

## Quick Start: Adding Plugin for Slug Generators & String Money

Register `payloadFieldsPlugin` in your Payload config:

```ts
import { payloadFieldsPlugin, slugField } from "@nexload-sdk/payload-fields";
import { buildConfig } from "payload";

export default buildConfig({
  collections: [
    {
      slug: "products",
      fields: [
        { name: "title", type: "text", required: true },
        ...slugField({ source: "title", generator: "product" }),
      ],
    },
  ],
  plugins: [
    payloadFieldsPlugin({
      slugGenerators: {
        product: async ({ sourceValue }) => {
          return `sku-${sourceValue.toLowerCase().replace(/\s+/g, "-")}`;
        },
      },
    }),
  ],
});
```

# Production Guides & Recipes

Audit options, events, privacy, and migration.

**Topic:** guides
**Package:** `@nexload-sdk/payload-hooks` v2.1.0
**Canonical page:** https://gecut.github.io/nexload-sdk/packages/payload-hooks/guides/
## Audit options

| Option | Default | Behavior |
| --- | --- | --- |
| `collections` | `"all"` | All collections or an array of slugs. |
| `exclude` | `[]` | Slugs to skip. Unknown requested or excluded slugs throw at config time. |
| `operations` | `["create", "update", "delete", "auth"]` | Enabled operations; add `"read"` to audit reads. |
| `logger` | SDK default logger | Custom logger with an `info` method. |

The plugin runs at order 1000 and appends hooks after existing hooks. Writes log once per document. Reads are off by default; when enabled, each request produces one list summary or single-read event. Auth auditing is on by default for auth collections; failed logins are not logged. Logging failures do not interrupt operations. Events contain identifiers and counts, never document bodies, emails, tokens, or other credentials.

## Events

* `payload.document.created`
* `payload.document.updated`
* `payload.document.deleted`
* `payload.documents.listed`
* `payload.document.read`
* `payload.auth.logged_in`
* `payload.auth.password_reset_requested`
* `payload.auth.password_reset`

Write event IDs may be absent. List events include a count rather than document contents or IDs.

## Boundaries

Payload creates its implicit default `users` collection after plugins run. Declare the auth collection explicitly to audit its auth and write events. Write hooks emit events before transaction commit, so a later rollback can leave an event for a change that did not persist.

## Migrate from `logOperation`

`logOperation` is deprecated. Remove per-collection hooks and register the plugin once:

```ts
// Before: hooks: { afterChange: [logOperation("afterChange")] }
import { auditPlugin } from "@nexload-sdk/payload-hooks";

const plugins = [auditPlugin()];
```

The preset also includes `auditPlugin` by default; do not register it twice. See [Payload Preset](/nexload-sdk/packages/payload-preset/).

## Multi-Resource Operations Tree

In real-world applications, operations should be grouped by domain resources instead of maintaining a flat list. `@nexload-sdk/payload-operations` supports arbitrary tree nesting:

```ts
import { defineCMSOperations, operation } from "@nexload-sdk/payload-operations";
import { z } from "zod";

const dateCodec = z.codec(z.iso.datetime(), z.date(), {
  decode: (s) => new Date(s),
  encode: (d) => d.toISOString(),
});

export const cmsOperations = defineCMSOperations({
  auth: {
    login: operation({
      input: z.object({ email: z.string().email(), password: z.string().min(8) }),
      output: z.object({ token: z.string(), userId: z.string() }),
      errors: {
        INVALID_CREDENTIALS: { status: 401, message: "Invalid email or password." },
      },
    }),
    me: operation({
      input: z.void(),
      output: z.object({ email: z.string().email(), id: z.string() }),
    }),
  },

  inventory: {
    checkStock: operation({
      input: z.object({ sku: z.string() }),
      output: z.object({ available: z.number().int(), sku: z.string() }),
    }),
    reserve: operation({
      input: z.object({ sku: z.string(), quantity: z.number().int().positive() }),
      output: z.object({ reservationId: z.string(), expiresAt: dateCodec }),
      errors: {
        OUT_OF_STOCK: {
          status: 409,
          message: "Insufficient quantity available.",
          data: z.object({ available: z.number().int().nonnegative() }),
        },
      },
    }),
  },

  orders: {
    create: operation({
      input: z.object({
        items: z.array(z.object({ sku: z.string(), quantity: z.number().int() })),
      }),
      output: z.object({ orderId: z.string(), totalCents: z.number() }),
      errors: {
        PAYMENT_FAILED: {
          status: 402,
          message: "Payment declined by payment processor.",
          data: z.object({ gatewayCode: z.string() }),
        },
      },
    }),
  },
});
```

## Role-Based Access Control (RBAC) & Overrides

`access.default` is **strictly required** by `createPayloadEndpoints`. If missing, it throws `TypeError: createPayloadEndpoints requires access.default.` at configuration time.

You can specify default permissions and override them on a per-operation basis:

```ts
import { createPayloadEndpoints } from "@nexload-sdk/payload-operations/server";
import { cmsOperations } from "./contract";

export const operationEndpoints = createPayloadEndpoints({
  operations: cmsOperations,
  access: {
    // Required default rule: Must be authenticated
    default: ({ req }) => Boolean(req.user),

    // Granular overrides
    overrides: {
      auth: {
        login: () => true, // Publicly accessible
      },
      inventory: {
        checkStock: () => true, // Public read check
      },
      orders: {
        // Only administrators can perform bulk admin operations
        create: ({ req }) => req.user?.collection === "users",
      },
    },
  },
  handlers: { /* ... handlers matching cmsOperations ... */ },
});
```

* When access returns `false` for an unauthenticated request, the endpoint returns **HTTP 401 Unauthorized**.
* When access returns `false` for an authenticated request with insufficient rights, it returns **HTTP 403 Forbidden**.

### Request Body Size Limiting (`maxBodyBytes`)

`createPayloadEndpoints` limits incoming request bodies via `maxBodyBytes` (defaults to `1_048_576` bytes / 1 MiB):

* Validates the incoming `Content-Length` header upfront to reject oversized requests before buffering.
* Streams the request body while counting bytes, aborting if the limit is exceeded.
* Oversized requests return **HTTP 413 Payload Too Large** (`PAYLOAD_TOO_LARGE`).

## Database Transactions & Local API Handlers

Handlers receive the incoming `req: PayloadRequest`, giving you direct access to `req.payload` for database queries:

> \[!NOTE]
> **Database Transactions & Local API Invariants:**
>
> * **No automatic transactions:** Operations do not automatically begin or commit database transactions. If your operation requires transactional integrity, manage transactions explicitly using Payload's transaction API.
> * **Local API `overrideAccess: true`:** By default, Payload 3 `req.payload` Local API calls run with `overrideAccess: true`. If collection-level access control must be enforced for the current user, pass `{ overrideAccess: false, req }` in each Local API call.

```ts
handlers: {
  orders: {
    create: async ({ input, errors, req }) => {
      // 1. Validate permissions and inventory
      const outOfStockItems: string[] = [];

      for (const item of input.items) {
        const stockRecord = await req.payload.find({
          collection: "inventory",
          where: { sku: { equals: item.sku } },
          limit: 1,
          req,
        });

        if ((stockRecord.docs[0]?.quantity ?? 0) < item.quantity) {
          outOfStockItems.push(item.sku);
        }
      }

      if (outOfStockItems.length > 0) {
        throw errors.OUT_OF_STOCK({
          data: { available: 0 },
        });
      }

      // 2. Persist order with caller user context
      const newOrder = await req.payload.create({
        collection: "orders",
        data: {
          items: input.items,
          customer: req.user?.id,
          status: "confirmed",
        },
        req,
      });

      return {
        orderId: String(newOrder.id),
        totalCents: 5000,
      };
    },
  },
}
```

## Codec Wire Model & Serialization

`@nexload-sdk/payload-operations` uses a bidirectional Zod codec architecture on the wire:

* **Handler output is encoded:** The handler returns `z.output<output>`. The server encodes this output using `z.encodeAsync(output, result)`. Unknown keys on `z.object` schemas are automatically stripped, preventing database internals or secret properties from leaking to callers (`z.looseObject` or `.passthrough()` enables passing extra keys as an explicit opt-in).
* **Client decodes:** The client decodes the JSON response with `z.decodeAsync(output, json)`, reconstructing rich types like `Date`.
* **Defined errors are encoded/decoded identically:** Defined error `data` schemas undergo the same `z.encodeAsync` on the server and `z.decodeAsync` on the client.
* **Client sends original input:** The client pre-validates input with `safeParseAsync` (rejecting invalid calls upfront with 422 `INPUT_VALIDATION_FAILED`), then serializes and sends the caller's original input value (`z.input`). Defaults and transforms execute once on the server. The caller's input must be JSON-serializable.

### Codec Safety Rule for Outputs

Because outputs are encoded via `z.encodeAsync`, output schemas and defined-error `data` schemas must be **codec-safe**:

* Standard types (`z.string()`, `z.number()`, `z.boolean()`, `z.object()`, `z.array()`)
* Checks and overwrites (`z.string().trim()`, `z.string().toLowerCase()`)
* Symmetrical codecs (`z.codec(wireSchema, targetSchema, { decode, encode })`)

> \[!CAUTION]
> Unidirectional `.transform()` calls in output or error schemas cannot be encoded by `z.encodeAsync`. Returning such a schema from a handler causes the server to fail with **500 INTERNAL\_SERVER\_ERROR**. Always use `z.codec` for transformations in output schemas.

### Handling Dates with `z.codec`

To pass JavaScript `Date` instances between server handlers and client callers:

```ts
import { operation } from "@nexload-sdk/payload-operations";
import { z } from "zod";

export const dateCodec = z.codec(z.iso.datetime(), z.date(), {
  decode: (isoString) => new Date(isoString),
  encode: (dateObj) => dateObj.toISOString(),
});

export const getEvent = operation({
  input: z.object({ id: z.string() }),
  output: z.object({
    id: z.string(),
    scheduledAt: dateCodec, // Handler returns Date; wire sends ISO string; client receives Date
  }),
});
```

## Client Transport Plugins

The client uses an extensible middleware pipeline (`CMSClientPlugin`) that wraps every fetch request for both custom operations and native Payload SDK methods:

### 1. Built-in Timeout Plugin

Enforces strict client-side timeout thresholds with automatic `AbortSignal` management:

```ts
import { createCMSClient } from "@nexload-sdk/payload-operations/cms";
import { timeoutPlugin } from "@nexload-sdk/payload-operations/plugins/timeout";

const cms = createCMSClient({
  operations: cmsOperations,
  payload: { baseURL: "https://cms.example.com" },
  plugins: [
    timeoutPlugin({ timeout: 5_000 }), // 5-second timeout
  ],
});
```

### 2. Custom Authorization Bearer Plugin

Automatically attaches JWT tokens to outgoing requests:

```ts
import { defineClientPlugin } from "@nexload-sdk/payload-operations/client";

export const authBearerPlugin = (getToken: () => string | null) =>
  defineClientPlugin({
    name: "auth-bearer",
    wrapTransport: (next) => (request) => {
      const token = getToken();
      if (!token) return next(request);

      const headers = new Headers(request.init.headers);
      headers.set("Authorization", `Bearer ${token}`);

      return next({
        ...request,
        init: { ...request.init, headers },
      });
    },
  });
```

### 3. Distributed Tracing & Metrics Plugin

Inspect request latency and differentiate operation calls from native Payload SDK calls:

```ts
import { defineClientPlugin } from "@nexload-sdk/payload-operations/client";

export const tracingPlugin = defineClientPlugin({
  name: "tracing",
  wrapTransport: (next) => async (request) => {
    const started = performance.now();
    const response = await next(request);
    const duration = performance.now() - started;

    if (request.source === "operation" && request.operation) {
      console.log(`[Op: ${request.operation.path}] took ${duration.toFixed(2)}ms`);
    }

    return response;
  },
});
```

### 4. Pure Operations Client (Without Payload SDK)

If your frontend or BFF only calls custom operations and does not need the native Payload SDK:

```ts
import { createOperationsClient } from "@nexload-sdk/payload-operations/client";
import { timeoutPlugin } from "@nexload-sdk/payload-operations/plugins/timeout";

const client = createOperationsClient({
  baseURL: "https://cms.example.com",
  basePath: "/api/operations",
  operations: cmsOperations,
  plugins: [timeoutPlugin({ timeout: 5_000 })],
});

const stock = await client.inventory.checkStock({ sku: "TSHIRT-1" });
```

## Safe Error Pattern-Matching

Instead of messy `try/catch` blocks, use the `safe()` tuple utility. It differentiates declared business errors from catastrophic framework failures:

```ts
import { isDefinedError, isTimeoutError, safe } from "@nexload-sdk/payload-operations";

const [error, reservation, isDefined] = await safe(
  cms.operations.inventory.reserve({
    sku: "MACBOOK-M3",
    quantity: 1,
  })
);

// 1. Discriminated domain errors (statically typed by contract)
if (isDefined && isDefinedError(error, "OUT_OF_STOCK")) {
  console.warn("Out of stock! Available units:", error.data.available);
  return;
}

// 2. Client timeout error
if (isTimeoutError(error)) {
  console.error("The operation timed out after 5 seconds.");
  return;
}

// 3. Catastrophic errors (network failure, 500 server crash, malformed response)
if (error !== null || !reservation) {
  console.error("Unexpected error:", error);
  return;
}

// 4. Success path (fully typed output)
console.log("Reserved successfully! ID:", reservation.reservationId);
```

## Next.js App Router Integration (Server Actions)

Consume operations seamlessly in Next.js Server Actions with zero hydration overhead:

```ts
"use server";

import { cms } from "@/lib/cms";
import { isDefinedError, safe } from "@nexload-sdk/payload-operations";
import { revalidatePath } from "next/cache";

export async function placeOrderAction(formData: FormData) {
  const sku = String(formData.get("sku"));
  const quantity = Number(formData.get("quantity"));

  const [error, order, isDefined] = await safe(
    cms.operations.orders.create({
      items: [{ sku, quantity }],
    })
  );

  if (isDefined) {
    if (isDefinedError(error, "PAYMENT_FAILED")) {
      return { ok: false, error: "Payment was declined by payment gateway." };
    }
  }

  if (error) {
    return { ok: false, error: "An unexpected error occurred." };
  }

  revalidatePath("/orders");
  return { ok: true, orderId: order.orderId };
}
```

## Troubleshooting & Common Pitfalls

### 1. `INPUT_VALIDATION_FAILED` (No Network Request Sent)

Input validation happens on the client before the request is dispatched. If your client method throws or rejects immediately, check the Zod schema requirements (e.g. required string length, email regex, integer bounds).

### 2. Endpoint Responds with 401 or 403

`access.default` is required. The default access policy determines baseline permissions for all operations. If access returns `false` and `req.user` is absent, the endpoint returns **401 Unauthorized**. If `req.user` is present, it returns **403 Forbidden**. To make an operation publicly accessible, add an explicit override:

```ts
access: {
  default: ({ req }) => Boolean(req.user),
  overrides: {
    auth: { login: () => true },
  },
}
```

### 3. Route Returns 404 Not Found

* Verify that both client (`createCMSClient` or `createOperationsClient`) and `createPayloadEndpoints` use the identical `basePath` (e.g. `"/api/operations"`).
* Make sure you spread `...operationEndpoints` into Payload's `endpoints` array in `payload.config.ts`.
* Ensure `baseURL` contains only the origin and API mount, without query strings or trailing hash tags.

### 4. Browser CORS Pre-flight (`OPTIONS`) Failure

`createPayloadEndpoints` generates matching `OPTIONS` endpoints for every operation. Ensure your Payload server has CORS headers configured for your client origin:

```ts
// payload.config.ts
export default buildConfig({
  cors: ["https://myfrontend.com"],
  csrf: ["https://myfrontend.com"],
  endpoints: [...operationEndpoints],
});
```

### 5. Domain Error Was Downgraded to Internal Error

If a handler throws an error object that doesn't match the contract's defined status or code, the server boundary deliberately downgrades it to an `INTERNAL_ERROR` to protect internal stack traces from leaking. **Always use the handler's injected error factories**:

```ts
// Correct
throw errors.OUT_OF_STOCK({ data: { available: 5 } });

// Incorrect
throw new Error("Out of stock");
```

### 6. Endpoint Responds with 413 Payload Too Large

`createPayloadEndpoints` enforces `maxBodyBytes` (default 1 MiB / `1_048_576`). Requests exceeding this limit return `PAYLOAD_TOO_LARGE`. If your endpoint legitimately requires larger payloads, increase `maxBodyBytes`:

```ts
createPayloadEndpoints({
  operations,
  handlers,
  access: { default: () => true },
  maxBodyBytes: 10_485_760, // 10 MiB
});
```

### 7. Server Responds with 500 During Response Encoding

If your handler output schema uses a unidirectional `.transform()`, `z.encodeAsync` cannot invert it to JSON wire format and throws an error, resulting in a 500 `INTERNAL_SERVER_ERROR`. Replace unidirectional transforms in output schemas with `z.codec(wireSchema, targetSchema, { decode, encode })`.

## Migrating to 2.0

`@nexload-sdk/payload-operations` 2.0 introduces secure-by-default execution, strict boundary isolation, bidirectional codecs, and a lightweight standalone client.

### New in 2.0

* **Pure client entry (`@nexload-sdk/payload-operations/client`):** Standalone RPC client via `createOperationsClient` with zero runtime dependency on `payload` or `@payloadcms/sdk`.
* **Codec wire model:** Symmetrical output and defined-error encoding via `z.encodeAsync`, automatically dropping unknown `z.object` keys to prevent sensitive data leaks.
* **Bidirectional Date handling:** Full support for `Date` instances using `z.codec(z.iso.datetime(), z.date(), { decode, encode })`.
* **Request body limits:** Built-in `maxBodyBytes` (default 1 MiB) with fast-fail `Content-Length` checks and stream byte counting returning 413 `PAYLOAD_TOO_LARGE`.
* **Enforced access control:** `access.default` is required at config time; missing it throws `TypeError`.
* **Complete test coverage:** Full automated test suite for contract traversal, access evaluation, codec roundtrips, and SQLite integration.

### Breaking Changes & Migration Steps

#### 1. `createCMSClient` moved to `@nexload-sdk/payload-operations/cms`

The integrated client that wraps the native `PayloadSDK` now lives in its own `./cms` subpath:

Before (1.0):

```ts
// Exported from package root in 1.0 (removed from root in 2.0)
// import { createCMSClient } from "<package-root>";
```

After (2.0):

```ts
import { createCMSClient } from "@nexload-sdk/payload-operations/cms";
```

#### 2. `timeoutPlugin` moved to `@nexload-sdk/payload-operations/plugins/timeout`

The timeout plugin is no longer exported from the package root:

Before (1.0):

```ts
// Exported from package root in 1.0 (removed from root in 2.0)
// import { timeoutPlugin } from "<package-root>";
```

After (2.0):

```ts
import { timeoutPlugin } from "@nexload-sdk/payload-operations/plugins/timeout";
```

#### 3. `createOperationsClient` is public in `@nexload-sdk/payload-operations/client`

For clients that do not need the Payload REST SDK, import `createOperationsClient` from `./client`:

Before (1.0):

```ts
// In 1.0, only createCMSClient was available (requiring @payloadcms/sdk)
const cms = createCMSClient({
  operations,
  payload: { baseURL: "https://cms.example.com" },
});
```

After (2.0):

```ts
// Pure RPC client with zero @payloadcms/sdk dependency
import { createOperationsClient } from "@nexload-sdk/payload-operations/client";

const client = createOperationsClient({
  baseURL: "https://cms.example.com",
  operations,
});
```

#### 4. Client sends original input value

Clients pre-validate input with `safeParseAsync` and then serialize and transmit the original input value (`z.input`). Defaults and transformations execute once on the server. Input values must be JSON-serializable:

Before (1.0):

```ts
// Client transformed values before transmission
const input = z.string().transform((val) => val.trim());
```

After (2.0):

```ts
// Transforms and defaults execute once on the server; caller passes original input
const input = z.string().trim();
```

#### 5. `access.default` is required in `createPayloadEndpoints`

Omitting `access.default` now throws a `TypeError` at config time instead of silently defaulting to `Boolean(req.user)`:

Before (1.0):

```ts
// access.default was optional
const endpoints = createPayloadEndpoints({
  operations,
  handlers,
});
```

After (2.0):

```ts
// access.default is strictly required
const endpoints = createPayloadEndpoints({
  operations,
  handlers,
  access: {
    default: ({ req }) => Boolean(req.user),
  },
});
```

#### 6. Handler return type is `z.output<output>` and is encoded

Handlers must return `z.output<output>`. The server encodes the result with `z.encodeAsync`, and unrecognized keys on `z.object` schemas are dropped:

Before (1.0):

```ts
// Handlers could return extra unmodeled fields that leaked to the client
handlers: {
  getUser: async () => ({
    id: "user-1",
    email: "user@example.com",
    passwordHash: "$2b$10$...", // leaked!
  }),
}
```

After (2.0):

```ts
// Handler returns z.output<output>; server encodes and drops unmodeled keys
handlers: {
  getUser: async () => ({
    id: "user-1",
    email: "user@example.com",
  }),
}
```

#### 7. Output and error-data schemas must be codec-safe

Unidirectional `.transform()` calls in output or error-data schemas cannot be encoded by `z.encodeAsync` (which causes a 500 error). Use `z.codec` instead:

Before (1.0):

```ts
// One-way transform in output schema
output: z.object({
  expiresAt: z.iso.datetime().transform((s) => new Date(s)),
})
```

After (2.0):

```ts
// Bidirectional codec using z.codec
const dateCodec = z.codec(z.iso.datetime(), z.date(), {
  decode: (s) => new Date(s),
  encode: (d) => d.toISOString(),
});

output: z.object({
  expiresAt: dateCodec,
})
```

#### 8. Zod floor raised to `>=4.1.0 <5.0.0`

Codec encoding and decoding require Zod 4.1+:

Before (1.0):

```json
"peerDependencies": {
  "zod": ">=4.0.0 <5.0.0"
}
```

After (2.0):

```json
"peerDependencies": {
  "zod": ">=4.1.0 <5.0.0"
}
```

#### 9. `@payloadcms/sdk` is an optional peer dependency

`@payloadcms/sdk` is only required if you import `@nexload-sdk/payload-operations/cms`:

Before (1.0):

```bash
# @payloadcms/sdk was a required peer dependency for all use cases
pnpm add @payloadcms/sdk
```

After (2.0):

```bash
# Install @payloadcms/sdk only if using createCMSClient from ./cms
pnpm add @payloadcms/sdk
```

#### 10. Request body size limit (`maxBodyBytes`)

Incoming request bodies exceeding `maxBodyBytes` (default 1 MiB) are now rejected with HTTP 413:

Before (1.0):

```ts
// Unbounded body reads could cause server out-of-memory errors
createPayloadEndpoints({ operations, handlers });
```

After (2.0):

```ts
// Bodies over maxBodyBytes (default 1_048_576 bytes) return 413 PAYLOAD_TOO_LARGE
createPayloadEndpoints({
  operations,
  handlers,
  access: { default: () => true },
  maxBodyBytes: 2_097_152, // Custom 2 MiB limit (optional)
});
```

***

## Migration from Legacy Custom Handlers

When migrating from ad-hoc Payload REST routes:

1. Move request/response validation logic into `operation({ input, output, errors })`.
2. Replace manual `new Response(JSON.stringify(...))` with standard async return values.
3. Remove manual `req.json()` calls; input is parsed and injected directly into `({ input })`.

# Overview & Quick Start

Type-safe custom application operations for Payload CMS with shared Zod contracts and client SDK.

**Topic:** overview
**Package:** `@nexload-sdk/payload-operations` v1.0.0
**Canonical page:** https://gecut.github.io/nexload-sdk/packages/payload-operations/
**Package:** `@nexload-sdk/payload-operations`

**Current released version:** `1.0.0`

Typed custom operations for Payload CMS with the native Payload REST SDK.

[npm](https://www.npmjs.com/package/@nexload-sdk/payload-operations) · [Source](https://github.com/gecut/nexload-sdk/tree/main/packages/payload-operations)

`@nexload-sdk/payload-operations` defines a single shared Zod contract, mounts it as secure Payload CMS REST endpoints, and exposes matching, fully typed RPC client methods beside the native `PayloadSDK`.

Use it for application commands, domain actions, and multi-step workflows that do not fit Payload's default collection CRUD API. Keep ordinary document reads and writes on `cms.payload`; put project-owned business operations under `cms.operations`.

***

## 10-Second Code Snippet

```ts
import { defineCMSOperations, operation } from "@nexload-sdk/payload-operations";
import { createCMSClient } from "@nexload-sdk/payload-operations/cms";
import { z } from "zod";

// 1. Define shared contract
export const operations = defineCMSOperations({
  inventory: {
    check: operation({
      input: z.object({ sku: z.string() }),
      output: z.object({ available: z.number().int() }),
    }),
  },
});

// 2. Consume from frontend or server action with full type inference
const cms = createCMSClient({
  operations,
  payload: { baseURL: "https://cms.example.com/api" },
});

const stock = await cms.operations.inventory.check({ sku: "TSHIRT-BLK-M" });
console.log(stock.available); // typed as number
```

## What You Get

* **Single Source of Truth**: Define input, output, and domain error schemas once; TypeScript infers both client and server types automatically.
* **Hierarchical Operation Trees**: Group operations logically (`auth.login`, `orders.create`, `inventory.reserve`) without flat route chaos.
* **Asynchronous Zod Parsing**: Full support for input transformations, client-side pre-flight sanitization, and output projections.
* **Discriminated Domain Errors**: Explicit error definitions with typed data payloads, status codes, and deterministic client pattern matching.
* **Native Payload Integration**: Handlers receive the authentic `PayloadRequest`, providing full access to `req.payload.find`, `req.payload.create`, and user session context.
* **Shared Transport Pipeline**: A unified fetch client with plugin support (timeouts, custom Bearer authentication, distributed tracing) shared between custom operations and the official Payload SDK.

## Core Concepts & Architecture

### 1. The Contract Model (`@nexload-sdk/payload-operations/contract`)

The contract is a shared, platform-neutral module containing only Zod schemas and metadata. It has **zero dependencies on Payload server internals**, making it 100% safe to import in browser bundles, Next.js Server Components, mobile clients, and worker threads.

### 2. Dual Boundary Validation & Codec Wire Model

* **Client Boundary**: Validates input before sending a network request. If invalid, fails immediately with `INPUT_VALIDATION_FAILED` without unnecessary HTTP traffic. The client sends the original JSON-serializable input (`z.input`), ensuring defaults and transforms execute once, on the server.
* **Server Boundary**: Re-validates the original input inside the Payload endpoint before executing the handler, protecting backend business logic. The handler returns `z.output<output>`. The server encodes output using `z.encodeAsync(output, result)`, dropping unknown keys so internal or secret fields never leak (`z.looseObject` allows extras as an explicit opt-in). Output and error-data schemas must be codec-safe (e.g. `z.codec` for dates). The client decodes the JSON response with `z.decodeAsync`.

### 3. Server Endpoints Mount (`@nexload-sdk/payload-operations/server`)

`createPayloadEndpoints` transforms your contract into Payload-compatible `Endpoint` definitions:

* `POST` handlers for each operation route (e.g. `/api/operations/inventory/reserve`).
* `OPTIONS` handlers to support CORS pre-flight across frontend origins.
* Required access control: `access.default` is required (e.g. `({ req }) => Boolean(req.user)`), throwing a `TypeError` at config time if omitted. Granular per-operation access overrides can be specified in `access.overrides`.
* Request body limits: Incoming request bodies are bounded by `maxBodyBytes` (defaults to 1 MiB / `1_048_576`), rejecting oversized payloads with 413 `PAYLOAD_TOO_LARGE`.

## Quick Start: End-to-End Implementation

### Step 1: Define the Shared Contract

Create `src/operations/contract.ts` (shared between client and server):

```ts
import { defineCMSOperations, operation } from "@nexload-sdk/payload-operations";
import { z } from "zod";

export const cmsOperations = defineCMSOperations({
  orders: {
    create: operation({
      input: z.object({
        sku: z.string().min(1),
        quantity: z.number().int().positive(),
      }),
      output: z.object({
        orderId: z.string(),
        createdAt: z.string(),
        totalAmount: z.number(),
      }),
      errors: {
        OUT_OF_STOCK: {
          status: 409,
          message: "Selected product is out of stock.",
          data: z.object({ available: z.number().int().nonnegative() }),
        },
      },
    }),
  },
});
```

### Step 2: Implement Handlers in Payload Config

In `src/payload.config.ts`, mount the operations into Payload's `endpoints` array:

```ts
import { buildConfig } from "payload";
import { createPayloadEndpoints } from "@nexload-sdk/payload-operations/server";
import { cmsOperations } from "./operations/contract";

const operationEndpoints = createPayloadEndpoints({
  operations: cmsOperations,
  basePath: "/api/operations",
  access: {
    // Required: access.default is mandatory
    default: ({ req }) => Boolean(req.user),
  },
  handlers: {
    orders: {
      create: async ({ input, errors, req }) => {
        // Query database via Payload Local API
        const item = await req.payload.find({
          collection: "inventory",
          where: { sku: { equals: input.sku } },
          limit: 1,
        });

        const stock = item.docs[0]?.stock ?? 0;
        if (stock < input.quantity) {
          throw errors.OUT_OF_STOCK({ data: { available: stock } });
        }

        // Create order document
        const order = await req.payload.create({
          collection: "orders",
          data: {
            sku: input.sku,
            quantity: input.quantity,
            customer: req.user?.id,
          },
        });

        return {
          orderId: String(order.id),
          createdAt: new Date().toISOString(),
          totalAmount: input.quantity * 25,
        };
      },
    },
  },
});

export default buildConfig({
  // Mount custom operations endpoints
  endpoints: [...operationEndpoints],
  // ... collections, db adapter, etc.
});
```

### Step 3: Instantiate and Call from Client

In your frontend application or Next.js App Router:

```ts
import { isDefinedError, safe } from "@nexload-sdk/payload-operations";
import { createCMSClient } from "@nexload-sdk/payload-operations/cms";
import { cmsOperations } from "./operations/contract";

const cms = createCMSClient({
  operations: cmsOperations,
  basePath: "/api/operations",
  payload: {
    baseURL: "https://cms.example.com",
    baseInit: { credentials: "include" },
  },
});

export async function submitOrder() {
  const [error, order, isDefined] = await safe(
    cms.operations.orders.create({
      sku: "ITEM-100",
      quantity: 2,
    })
  );

  if (isDefined && isDefinedError(error, "OUT_OF_STOCK")) {
    alert(`Only ${error.data.available} items left in stock.`);
    return;
  }

  if (error) {
    alert("Unexpected order failure.");
    return;
  }

  console.log("Order confirmed:", order.orderId);
}
```

# Production Guides & Recipes

Options, merge rules, ordering, and logging for the Payload preset.

**Topic:** guides
**Package:** `@nexload-sdk/payload-preset` v0.0.0
**Canonical page:** https://gecut.github.io/nexload-sdk/packages/payload-preset/guides/
## Options

| Option | Default | Behavior |
| --- | --- | --- |
| `persian` | `true` | Persian admin defaults; set `false` to disable. |
| `logger` | `true` | Bridge SDK options when `config.logger` is unset; set `false` to disable. |
| `fields` | `{}` | Options for `payloadFieldsPlugin`; set `false` to disable. |
| `audit` | `{}` | Options for `auditPlugin`; set `false` to disable. |

`payloadFieldsPlugin` runs at order 900 and `auditPlugin` at 1000. Ordinary host plugins run first, so their collections are available to both. The preset does not add, remove, or change collection fields. Define them with [Payload Schema](/nexload-sdk/packages/payload-schema/) and [Payload Fields](/nexload-sdk/packages/payload-fields/).

## Persian merge rules

The Persian plugin preserves host languages, fallback language, and default timezone. It adds Persian translations if absent, defaults the fallback to `fa`, and adds `Asia/Tehran` to supported timezones. It sets RTL only on existing `fa` locale objects without an explicit RTL value. It never creates localization or adds locales.

## Logger bridge

Call `configureLogger()` before `buildConfig()`. When `config.logger` is unset, the plugin uses the options form from `getPayloadLoggerConfig()`; Payload creates its own Pino logger from those options. Payload writes JSON in development unless `configureLogger({ destination })` supplies a stream. Rebuild the Payload config after forced SDK reconfiguration. See the [logger API](/nexload-sdk/packages/logger/api/).

## Audit boundaries

Audit reads are off by default; auth is on. The implicit default users collection is created after plugins run and is not audited: declare it explicitly. Write events are emitted before transaction commit and may describe rolled-back changes. See [Payload Hooks](/nexload-sdk/packages/payload-hooks/) for options and events.

The `getPayloadLoggerConfig()` bridge maps the SDK `success` threshold to Payload `warn`. Payload’s logger has no `success()` method.

## Entry Points & Signatures

### Root Entry: `@nexload-sdk/payload-schema`

The root entry is pure and browser-safe. It does not import `payload` at runtime and can be used in client bundles, edge runtimes, or Node.

```ts
import {
  defineEntity,
  field,
  defaultIdSchema,
  PayloadSchemaError,
  isPayloadSchemaError,
} from "@nexload-sdk/payload-schema";
import type {
  BlockDefinitionOptions,
  BlocksFieldOptions,
  EntityDefinition,
} from "@nexload-sdk/payload-schema";
```

An entity created by `defineEntity()` has:

* `name: string`: The entity name.
* `idSchema: AnyCanonicalSchema`: Canonical ID schema (defaults to `defaultIdSchema`).
* `fields: BoundFields`: Frozen map of defined field definitions.
* `schema(factory)`: Derives custom Zod schemas with access to `{ fields, pick, z }`.
* `inspect()`: Returns structured entity and field inspection metadata.

### Payload Compilation Entry: `@nexload-sdk/payload-schema/payload`

This entry is Node/Payload configuration only. It imports Payload's `ValidationError` to construct canonical validation hooks.

```ts
import { payloadFields } from "@nexload-sdk/payload-schema/payload";

const facade = payloadFields(entity);
facade.all();          // Returns all compiled Payload Field[] configs
facade.field("title"); // Returns a single compiled Payload Field config
facade.pick(["title"]); // Returns picked Payload Field[] configs
```

* **Safety Check:** Calling `payloadFields()` with anything other than an entity instance produced by `defineEntity()` throws a `PayloadSchemaError` with code `INVALID_ENTITY` (phase: `"payload-compilation"`).
* **Fresh Containers:** Each compilation call produces fresh field configuration objects so mutations in Payload config do not pollute entity seeds.

## The Complete 15-Field Factory Catalog

`@nexload-sdk/payload-schema` provides 15 specialized factories under the `field` namespace. Every factory configures both the Payload field definition and the corresponding Zod schema.

```ts
import { defineEntity, field } from "@nexload-sdk/payload-schema";
import { z } from "zod";

export const catalogEntity = defineEntity({
  name: "CatalogItem",
  fields: {
    // 1. Text: Trimming, case conversion, length constraints, regex pattern
    title: field.text({
      required: true,
      trim: true,
      minLength: 3,
      maxLength: 120,
    }),

    // 2. Slug: Automatic Unicode NFKC normalization and URL hyphen-casing
    slug: field.slug({
      required: true,
      minLength: 3,
      maxLength: 140,
    }),

    // 3. Textarea: Multiline text with max length
    summary: field.textarea({
      required: true,
      trim: true,
      maxLength: 1000,
    }),

    // 4. Number: Integer, safe integer checks, min/max range, step multiples
    stock: field.number({
      integer: true,
      safe: true,
      minimum: 0,
      defaultValue: 0,
    }),

    // 5. Money: Minor-unit integer (cents/rials) with explicit currency metadata
    price: field.money({
      currency: "USD",
      minimum: 0,
      required: true,
    }),

    // 6. Boolean: Checkbox field with boolean casting
    isActive: field.boolean({
      defaultValue: true,
    }),

    // 7. Date: Timezone-aware ISO datetime string with min/max bounds (hook accepts JS Date)
    publishedAt: field.date({
      minimum: "2024-01-01T00:00:00.000Z",
      nullable: true,
    }),

    // 8. Select: Single or multi-choice enums with custom admin labels
    tier: field.select({
      values: ["standard", "premium", "enterprise"] as const,
      labels: { enterprise: "Enterprise SLA" },
      defaultValue: "standard",
    }),
    badges: field.select({
      hasMany: true,
      values: ["new", "sale", "featured"] as const,
    }),

    // 9. Relationship: Single or polymorphic relationships
    category: field.relationship({
      relationTo: "categories",
      required: true,
    }),
    authorOrTeam: field.relationship({
      relationTo: ["authors", "teams"] as const,
      hasMany: false,
      idSchema: z.string().uuid(),
    }),

    // 10. Upload: Media asset relationship
    heroImage: field.upload({
      relationTo: "media",
      required: true,
    }),

    // 11. Group: Nested object schema and Payload named group
    seo: field.group({
      fields: {
        metaTitle: field.text({ maxLength: 70 }),
        metaDesc: field.textarea({ maxLength: 160 }),
      },
    }),

    // 12. Array: Repeatable rows with row count constraints
    variants: field.array({
      minRows: 1,
      maxRows: 10,
      fields: {
        sku: field.text({ required: true, uppercase: true }),
        price: field.money({ currency: "USD", required: true }),
      },
    }),

    // 13. Blocks: Discriminated polymorphic blocks with child validation
    layout: field.blocks({
      minRows: 1,
      maxRows: 10,
      blocks: {
        hero: {
          fields: {
            headline: field.text({ required: true }),
            subheading: field.text({ nullable: true }),
          },
        },
        quote: {
          fields: {
            quoteText: field.textarea({ required: true }),
            author: field.text({ required: true }),
          },
        },
      },
    }),

    // 14. RichText: Requires explicit AST schema validator
    description: field.richText({
      schema: z.record(z.string(), z.unknown()),
    }),

    // 15. Native: Escape hatch for custom/unsupported Payload field types
    coordinates: field.native({
      payload: { type: "point" },
      schema: z.tuple([z.number(), z.number()]),
    }),
  },
});
```

## Static Defaults vs. Dynamic Defaults

`@nexload-sdk/payload-schema` separates static values from runtime functions:

```ts
// 1. Static Default: Validated during defineEntity() at startup
field.number({
  defaultValue: 100,
});

// 2. Dynamic Default: Evaluated at runtime by Payload per write request
field.date({
  dynamicDefaultValue: ({ req, user, locale }) => new Date().toISOString(),
});
```

* Providing both `defaultValue` and `dynamicDefaultValue` throws `CONFLICTING_DEFAULT_CONFIGURATION`.
* Direct assignment to `payload.defaultValue` is prohibited and throws `RESERVED_PAYLOAD_OPTION`.
* Defaults do not append `.default()` to derived Zod schemas, keeping API request validation explicit.

## Advanced Schema Derivation Patterns

Use `entity.schema()` to generate input schemas for mutations, projections, and forms:

### 1. Picking Fields with Strictness and `optional: "auto"`

```ts
export const createItemSchema = catalogEntity.schema(({ pick }) =>
  pick(["title", "slug", "price", "stock", "layout"], {
    optional: "auto", // Automatically marks non-required fields optional
    strict: true,     // Rejects unexpected fields
  })
);
```

* With `{ optional: "auto" }`, any field whose definition does not have `required: true` becomes `.optional()`.
* An explicit `required` array (e.g. `required: ["stock"]`) takes precedence and forces listed keys to be required.

### 2. Custom Field Transformations

```ts
export const catalogCardSchema = catalogEntity.schema(({ fields, z }) =>
  z.object({
    title: fields.title,
    slug: fields.slug,
    // Transform minor-unit cents into formatted dollar string
    priceDisplay: fields.price.transform((cents) => `$${(cents / 100).toFixed(2)}`),
  })
);
```

### 3. Cross-Field Refinements

```ts
export const inventoryUpdateSchema = catalogEntity.schema(({ fields, z }) =>
  z
    .object({
      stock: fields.stock,
      isActive: fields.isActive,
    })
    .refine((data) => !(data.stock === 0 && data.isActive), {
      message: "Cannot mark an out-of-stock item as active.",
      path: ["isActive"],
    })
);
```

### 4. Inferring TypeScript Types

```ts
export type CreateItemInput = z.infer<typeof createItemSchema>;
export type CatalogCardDTO = z.infer<typeof catalogCardSchema>;
```

## Intrinsic Normalization & Runtime Semantics

### Normalization on Writes

When writing data through the Payload Admin UI or `payload.create` / `payload.update`, canonical normalization executes automatically in `beforeValidate`:

```ts
// Local API Write:
await payload.create({
  collection: "catalog",
  data: {
    title: "   Vintage Leather Jacket   ", // Normalized to "Vintage Leather Jacket"
    slug: "Vintage Leather Jacket",        // Normalized to "vintage-leather-jacket"
    variants: [
      { sku: "vlj-01", price: 15000 },     // sku normalized to "VLJ-01"
    ],
  },
});
```

### Null Semantics

Payload CMS represents empty or cleared fields as `null`. Canonical `beforeValidate` hooks pass `null` through unchanged for all field kinds (including nested children in groups, arrays, and blocks), matching `undefined` semantics:

* Clearing optional fields with `null` succeeds without raising Zod type errors.
* Required fields without a value fail Payload's built-in validation ("This field is required."), reporting the exact path and field label.

### Date Objects

In `field.date()`, the runtime Payload hook accepts JavaScript `Date` instances and normalizes valid dates to ISO 8601 strings. Canonical and derived Zod schemas continue to expect ISO strings.

### Codec Safety

Built-in field normalizations (`trim`, `lowercase`, `uppercase`, `slug`, `date`) are implemented using Zod `.overwrite()` instead of unidirectional `.transform()`. This preserves codec reversibility so derived schemas can be encoded with `z.encode` (e.g., in `@nexload-sdk/payload-operations` outputs).

***

## Known Limitations

* **No inline Admin validation:** Validation is enforced via `beforeValidate` hooks. The package does not generate inline Admin `validate` functions.
* **Custom `options.schema` transforms are not codec-safe:** Custom transformations passed to `options.schema(...)` cannot be inverted by `z.encode`. Use `.refine()` or `.overwrite()` if schemas are used in operation responses.
* **Strict pick default:** Calling `pick(keys)` without `{ optional: ... }` makes every key strictly required. Use `{ optional: "auto" }` to inherit field-level optionality.

***

## Troubleshooting & Diagnostics

### 1. `SCHEMA_UNAVAILABLE`

Occurs when deriving a schema that includes a `field.native()` defined without a `schema` parameter, or a container (`group`, `array`, `blocks`) that includes a schema-less native field.

```ts
// Solution: Provide the schema parameter
field.native({
  payload: { type: "point" },
  schema: z.tuple([z.number(), z.number()]),
});
```

### 2. `INVALID_ENTITY`

Thrown when passing a non-entity value to `payloadFields()`:

```ts
import { payloadFields } from "@nexload-sdk/payload-schema/payload";

// Throws PayloadSchemaError: INVALID_ENTITY
// @ts-expect-error - intentional misuse with non-entity
payloadFields({ name: "NotAnEntity" });
```

### 3. `ASYNC_CANONICAL_SCHEMA_UNSUPPORTED`

Payload's field validation hooks run synchronously. Canonical parsing raises `ASYNC_CANONICAL_SCHEMA_UNSUPPORTED` when a schema is async (e.g., contains `.refine(async ...)` or `.transform(async ...)`): at `defineEntity` time only when validating a static `defaultValue`, otherwise when the Payload hook parses a value during writes. Move async checks into custom Payload collection hooks or derived API schemas.

### 4. Safe Introspection with `inspect()`

Inspect the runtime structure and field configurations safely without exposing internal state:

```ts
const inspection = catalogEntity.inspect();
console.log(inspection.name); // "CatalogItem"
console.log(inspection.fields.price.currency); // "USD"
```

### 5. Error Handling Helper

Use `isPayloadSchemaError()` to catch and format entity definition failures:

```ts
import { isPayloadSchemaError } from "@nexload-sdk/payload-schema";

try {
  // defineEntity(...)
} catch (error) {
  if (isPayloadSchemaError(error)) {
    console.error(`[${error.code}] in phase ${error.phase}: ${error.message}`);
  }
}
```

## Migrating to 3.0

Version 3.0 brings browser safety, codec compatibility, blocks fields, and predictable null handling.

### New in 3.0

* **`field.blocks()`**: Discriminated polymorphic block containers with per-block schemas and child validation hooks.
* **`pick(..., { optional: "auto" })`**: Automatically marks fields without `required: true` as optional in derived schemas while preserving explicit required overrides.
* **`Date` accepted by the date hook**: The runtime `field.date()` hook accepts JavaScript `Date` instances and normalizes valid dates to ISO 8601 strings.
* **Composite child optionality & nullability**: Inside `group`, `array`, and `blocks`, non-required child fields are automatically optional and accept `null` (`key?: T | null`), so stored Payload documents with empty fields or rows omitting optional children parse cleanly.
* **Reserved block child names**: Block child fields cannot be named `id`, `blockName`, or `blockType`; doing so throws `PayloadSchemaError` (`INVALID_FIELD_CONFIGURATION`) at definition time.

### Breaking Changes

Below are the before and after patterns for each breaking change.

### 1. Payload Compilation Moved to `/payload` Subpath

Entity definitions no longer carry a `.payload` facade on the entity object. Payload compilation is now imported from `@nexload-sdk/payload-schema/payload` (Node-only), making the root entry browser-safe.

**Before (2.0):**

```ts
import { defineEntity, field } from "@nexload-sdk/payload-schema";

export const articleEntity = defineEntity({ /* ... */ });

export const Articles = {
  slug: "articles",
  // In 2.0, compiled fields were accessed via property on the entity:
  fields: articleEntity["payload"]["all"](),
};
```

**After (3.0):**

```ts
import { defineEntity, field } from "@nexload-sdk/payload-schema";
import { payloadFields } from "@nexload-sdk/payload-schema/payload";

export const articleEntity = defineEntity({
  name: "Article",
  fields: {
    title: field.text({ required: true }),
  },
});

export const Articles = {
  slug: "articles",
  fields: payloadFields(articleEntity).all(),
};
```

### 2. Zod Peer Dependency Floor Raised to 4.1

Zod 4.1.0 or higher is required to support Zod codec methods (`z.encode` / `z.decode`).

**Before (2.0):**

```json
{
  "peerDependencies": {
    "zod": ">=4.0.0 <5.0.0"
  }
}
```

**After (3.0):**

```json
{
  "peerDependencies": {
    "zod": ">=4.1.0 <5.0.0"
  }
}
```

### 3. Null Passes Canonical Validation Hooks

In 2.0, clearing an optional field by passing `null` caused Zod to throw a `ValidationError` unless the field was explicitly declared `nullable: true`. In 3.0, `null` passes through canonical hooks unchanged (like `undefined`), allowing empty optional fields to clear cleanly.

**Before (2.0):**

```ts
// Required nullable: true to allow clearing optional fields in database writes:
subtitle: field.text({ nullable: true }),

// Clearing without nullable: true threw ValidationError:
// "Expected string, received null"
await payload.update({
  collection: "articles",
  id: "1",
  data: { subtitle: null },
});
```

**After (3.0):**

```ts
// Optional fields without nullable: true allow null to pass through:
subtitle: field.text(),

// Clears field cleanly; required fields fail Payload's "This field is required." check:
await payload.update({
  collection: "articles",
  id: "1",
  data: { subtitle: null },
});
```

### 4. Date Objects Accepted by Date Hook

In 2.0, passing JavaScript `Date` instances to Payload writes failed canonical validation because the hook strictly required ISO strings. In 3.0, the runtime hook accepts valid `Date` objects and converts them to ISO strings.

**Before (2.0):**

```ts
// Threw ValidationError: "Expected string, received object"
await payload.create({
  collection: "events",
  data: {
    eventDate: new Date(),
  },
});
```

**After (3.0):**

```ts
// Accepted and normalized to ISO string by runtime hook:
await payload.create({
  collection: "events",
  data: {
    eventDate: new Date(),
  },
});
```

### 5. Built-in Normalizations Are Codec-Safe (`.overwrite`)

In 2.0, text transformations like `trim: true` and `lowercase: true` used unidirectional `.transform()`, which causes `z.encode` to fail. In 3.0, normalizations use `.overwrite()`, making derived schemas compatible with codec encoding.

**Before (2.0):**

```ts
import { defineEntity, field } from "@nexload-sdk/payload-schema";
import { z } from "zod";

const productEntity = defineEntity({
  name: "Product",
  fields: {
    title: field.text({ trim: true }),
  },
});

const productSchema = productEntity.schema(({ fields }) => fields.title);
// Failed: unidirectional transform cannot be encoded
z.encode(productSchema, "  widget  ");
```

**After (3.0):**

```ts
import { defineEntity, field } from "@nexload-sdk/payload-schema";
import { z } from "zod";

const productEntity = defineEntity({
  name: "Product",
  fields: {
    title: field.text({ trim: true }),
  },
});

const productSchema = productEntity.schema(({ fields }) => fields.title);
// Succeeds: .overwrite() produces codec-safe schemas for operation outputs
const encoded = z.encode(productSchema, "  widget  ");
```

### 6. Composite Children Without `required: true` Are Optional and Nullable

In 2.0, composite containers (`group`, `array`, `blocks`) constructed their canonical object schemas directly from child schemas, causing stored documents with `null` (Payload's empty field representation) or rows omitting optional children to fail validation. In 3.0, any child field not declared `required: true` inside a composite container is automatically optional and nullable (`child.schema.nullable().optional()`).

**Before (2.0):**

```ts
const userEntity = defineEntity({
  name: "User",
  fields: {
    meta: field.group({
      fields: {
        tag: field.text({ required: true }),
        note: field.text(), // In 2.0, note was required in canonical schema
      },
    }),
  },
});

// Stored Payload document with empty note failed canonical parse:
// "Invalid input: expected string, received null"
userEntity.fields.meta.schema.parse({ tag: "vip", note: null });
```

**After (3.0):**

```ts
const userEntity = defineEntity({
  name: "User",
  fields: {
    meta: field.group({
      fields: {
        tag: field.text({ required: true }),
        note: field.text(), // In 3.0, non-required child is optional and nullable (key?: string | null)
      },
    }),
  },
});

// Parses cleanly for both null and omitted values:
userEntity.fields.meta.schema.parse({ tag: "vip", note: null }); // { tag: "vip", note: null }
userEntity.fields.meta.schema.parse({ tag: "vip" });             // { tag: "vip" }
```

### 7. Reserved Child Field Names in Blocks

In 3.0, block definitions reject child fields named `id`, `blockName`, or `blockType` at definition time with `PayloadSchemaError` (`INVALID_FIELD_CONFIGURATION`), as these names are reserved by Payload blocks runtime metadata.

**Before (2.0):**
Blocks were not supported in 2.0.

**After (3.0):**

```ts
// Throws PayloadSchemaError (code: "INVALID_FIELD_CONFIGURATION"):
field.blocks({
  blocks: {
    hero: {
      fields: {
        id: field.text(), // Reserved name: throws at definition time
      },
    },
  },
});
```

Define canonical field validation and normalization once, then reuse it across Payload CMS fields and Zod schemas.

**Package:** `@nexload-sdk/payload-schema`

Canonical Payload field definitions with reusable Zod schemas.

[npm](https://www.npmjs.com/package/@nexload-sdk/payload-schema) · [Source](https://github.com/gecut/nexload-sdk/tree/main/packages/payload-schema)

`@nexload-sdk/payload-schema` eliminates double-declaration of data validation rules in Payload CMS applications. Define intrinsic validation and normalization once, compile it into ordinary Payload collection fields, and expose the identical Zod schemas to client forms, server actions, and API boundaries.

***

## 10-Second Code Snippet

```ts
import { defineEntity, field } from "@nexload-sdk/payload-schema";
import { payloadFields } from "@nexload-sdk/payload-schema/payload";
import { z } from "zod";

// 1. Define intrinsic fields once (pure & browser-safe)
export const productEntity = defineEntity({
  name: "Product",
  fields: {
    title: field.text({ required: true, trim: true, minLength: 3 }),
    slug: field.slug({ required: true }),
    price: field.money({ currency: "USD", required: true }),
    stock: field.number({ integer: true, safe: true, defaultValue: 0 }),
  },
});

// 2. Export directly to Payload Collection (Node-only)
export const Products = {
  slug: "products",
  fields: payloadFields(productEntity).all(),
};

// 3. Derive Zod schemas for forms, Next.js server actions, or RPC
export const createProductSchema = productEntity.schema(({ pick }) =>
  pick(["title", "slug", "price", "stock"], { optional: "auto" })
);
export type CreateProductInput = z.infer<typeof createProductSchema>;
```

## Core Concepts & Invariants

### 1. One Intrinsic Contract

A field definition owns only the rules intrinsic to that field's value (e.g. "a product title must be 3-120 characters and trimmed"). Application-specific workflow rules (e.g. "is this field optional during draft creation?") belong in derived schemas, not in the core entity definition.

### 2. Dual Boundary Compilation

* Root `@nexload-sdk/payload-schema` is pure and browser-safe (`field`, `defineEntity`, `defaultIdSchema`, `PayloadSchemaError`). Entities expose `name`, `idSchema`, `fields`, `schema()`, and `inspect()`.
* `payloadFields(entity)` from `@nexload-sdk/payload-schema/payload` compiles standard Payload fields with canonical normalization appended to `beforeValidate`. Rejects non-entities with `PayloadSchemaError` (`code: "INVALID_ENTITY"`).
* `entity.schema()` produces pure Zod schemas reflecting the exact same constraints.

### 3. Synchronous Canonical Schemas

Canonical schemas must execute synchronously. If a schema is async, `ASYNC_CANONICAL_SCHEMA_UNSUPPORTED` is raised during canonical parsing: at `defineEntity` time only when validating a static `defaultValue`, otherwise when the Payload hook parses a value.

### 4. Non-Goals

The package does not create collections, own access control, replace Payload-generated types, or manage database migrations. Payload remains authoritative for persistence types and database schema.

## Quick Start: Building a Complete Entity

```ts
import { defineEntity, field } from "@nexload-sdk/payload-schema";
import { payloadFields } from "@nexload-sdk/payload-schema/payload";

export const articleEntity = defineEntity({
  name: "Article",

    title: field.text({ required: true, trim: true, minLength: 5 }),
```
